# 有人云巡站客户端（Windows / macOS）

[有人云](https://www.usr.cn) 平台的第三方桌面客户端：批量巡检设备、自动截图归档、
离线/数据陈旧告警、历史数据留档。Electron 壳 + Python 后端，界面是本地网页。

> 本仓库是**干净版本**：不含任何账号、密码、登录缓存、巡检截图与历史数据，
> 也不含任何公司标识。克隆下来后需要自己添加账号。

当前版本 **v1.4.3**（与 `package.json` 的 `version` 一致）。

## 〇、功能

- **巡站**：按账号批量拉取设备最新值，直接画成卡片图存档，跑完自动打包 zip
- **监控**：后台常驻，按规则比对并推系统通知，离线/数据陈旧/恢复都提醒，重复告警去重；
  **点通知可跳转到对应站点**
- **数据时间**：列表与实时卡片上的「X 分钟前」按当前时钟**实时走动**，
  在线/数据陈旧也随当前时钟复判，不会停在上一轮巡检的旧时间上
- **控制下发**：可写变量（写数值 / 开关）支持下发，**二次确认**后才真正发到设备
- **历史**：自动采样落盘，可按账号/设备查历史值；折线图横轴按所选范围铺满，跨天按日期标刻度，
  鼠标悬浮可看每个点的确切时间与数值，只有真离线才断线
- **设备列表**：支持排序与按账号搜索；**复制站点名称**一键进剪贴板；
  常看的站点可以**置顶**，固定排在最前
- **单个变量刷新**：只重采某个变量，不重绘整页
- **右键菜单**：输入框有剪切 / 复制 / 粘贴 / 全选；站点、设备行上有「复制站点名称」
  「置顶该站 / 取消置顶该站」「刷新这台设备的实时数据」
- **关于页**：显示版本、本次新增，以及 **GitHub 项目地址入口**（点击用系统浏览器打开）

### v1.4.3 修订（版本号不变）

**一、平台限流的钱花在哪：请求次数，不是点数。**
实测同一账号：一台设备 14 个点、每 3 秒一发，第 6 次就被拒（累计才 84 个点）；
把 1054 个点打成一发、每 3 秒连发 15 次全过。所以以前「每台三发（设备信息 + 变量定义 + 最新值）
× 94 台 × 7 线程并发」正好是最糟的形状。现在：

- 设备信息不再单独发 —— 设备列表接口同一个响应里就带 `projectName` / `templateName` /
  `deviceName` / `address` / `onlineOffline`（`dev_meta()`），这一项从「每台每轮 1 发」变成 0 发；
- 变量定义按 `DEF_TTL`（默认 1800 秒）缓存，并且**落盘**（`登录缓存/变量定义缓存.json`，原子写）——
  监控进程拉过的，截图进程点开就能用；截图的每个批次都是新进程，不落盘等于每批重拉 47~94 发；
- 最新值整个账号合批一发（`fetch_last_batch()`，>2000 点再分片），返回项带 `cusdeviceNo` 按设备索引；
- 相邻请求排队 `PACE_GAP = 0.34`（≈3 发/秒）；HTTP 连接按线程复用（keep-alive），单发从 0.38 秒降到 0.18 秒。
- `BACKOFF_429` 从 1800 秒改 60 秒（实测 20 秒就恢复），限流后按 `retry_in` 20 秒级回来重跑本轮，
  不再白等半小时留下一整片空白。

**二、「没问到」不再等于「离线」。**
平台的拒绝是隐形的：`status` 回 5144 / 5004 / 42013，`data` 给 `null` 或空 list，外形与「设备确实没数据」
完全一样。以前代码不看 `status` 直接取 `data`，于是把「没问着」判成了「设备离线、变量全是 -」。
现在所有取数路径统一过 `check_status()` / `api_data()`，拒绝抛 `ApiReject`（带 `kind` / `note`），
新增状态 `unknown`「未取到」：界面显示上一轮的数值 + 一行橙色原因（`平台拒绝:请求频率超限` 等），
**不报警、不改状态**；从来没成功过的设备记「未巡」，不凭空判离线。截图上的徽标同样写「● 未取到」。
被拒的合批按**设备**二分拆小定位（不能按点拆 —— 切在设备边界上会把邻台一起带进失败）：
一台没权限只影响它自己。登录失效（4013 / 1702）清缓存重登一次，多线程同时撞上只登一次。

**三、只补跑没数据的站。**
巡站页新增「只跑没数据的 N 台」：N 由 `_empty_devices()` 只读报告和磁盘算出（`offline` / `blank` /
`unknown` 或 png 不见了；数据陈旧算有数据）。补跑**复用原批次目录**，不新建批次：

- 截图同名覆盖（`keep_map()` 从已有文件名里取回清洗后的设备名，`shoot(keep=...)`），
  否则批次目录的图片数会比报告多，「报告条数 = png 张数 = zip 内张数」就对不上；
- 报告按**设备编号**就地合并（`merge_report()`），没用跑的几十台原样保留、位置不动，
  汇总按合并后重算；不能用站名当键 —— 同一工区有好几个站同名，会盖掉别人的条目；
- 压缩包重打同名，不生成第二个「同一批」的包；`_runner` 补跑时不清 `ST['results']`，
  页面列表始终是全部站点。

**四、单张重拍。**
截图弹窗新增「⟳ 重新获取这张截图」：只按设备编号定位（`_find_shot()` 只认编号，站名会重），
后台线程跑、前端 400ms 轮询（`/api/reshotstat`），不占整批的 `running` 状态；
拍失败**不写报告、不删旧图**，界面继续显示原来那张。整批正在跑时直接拒绝重拍
（两边同时写 `巡站报告.json`，谁后写谁赢，会出现「刚重拍的又变回旧的」）。

**五、顺手：账号行的台数统计一直是错的。**
`st['status']` 是中文（在线 / 数据陈旧 / 离线 / 采集异常），旧代码拿它去比英文键 `cnt`，
永远对不上，整批落进 `offline`。现在走 `CNT_KEY` 翻译表，并单列 `unknown`。

### v1.4.3 新增

**一、默认开硬件加速，崩过才降级。**
以前为了躲 `GPU process isn't usable. Goodbye.`（远程桌面 / 旧显卡驱动下独立 GPU 进程起不来），
默认关掉硬件加速并加 `in-process-gpu`，整页合成全走 CPU，长列表滚动和拖分栏都在软合成上跑。
现在默认开硬件加速，只有**本机实测崩过**才转软件渲染：GPU 进程 10 分钟内崩 2 次即降级并自动重启；
降级后撑满 14 天再试一次硬件，再失败期限翻倍（上限 60 天）。
判定逻辑单独放在 `gpu_mode.js`（纯函数，不碰 Electron / 磁盘，可脱离主进程跑断言），
主进程只负责读盘、调 `decide()`、把状态写回 `渲染模式.json`。
「上次硬件模式没走到成功标记就没了」是唯一能在「GPU 一起来就带走整个进程」时留下证据的办法，
所以启动后要等页面加载完成 + 12 秒无崩溃才算确认。打包漏拷 `gpu_mode.js` 时判定走异常分支退回软件渲染，至少保证能开。

**二、三栏宽度可以拖。**
账号栏和右侧栏之间原本那条直的分隔线换成可拖动的：平时 2px 浅灰，鼠标压上去变蓝、浮出三个点当抓手。
拖宽一栏时另一栏自动让位（账号栏不低于 200、右侧栏不低于 260），中间设备列表保底 400 不被挤爆；
双击复原。宽度存 `localStorage`，下次打开还在。拖动只改 `flex-basis`，拖动期间变量名先按单行省略
（`body.resizing`），松手恢复折行并重画历史折线图。

**三、实时卡能搜变量了。**
一台设备能有三四百个变量。实时卡顶部加了搜索条，固定在卡片外不随内容滚走，输入即过滤，
右侧显示「命中 / 总数」，一个都不匹配时给提示而不是留白；Esc 或 ✕ 清空，换设备自动清空。
过滤只改行元素的 `display`，不重建 DOM，因此和「后台每 8 秒刷新」互不干扰，也不会冲掉正在输入的值。

**四、实时卡刷新改成原地更新。**
以前每次刷新都把整张卡的 `innerHTML` 换一遍，311 行要重排一次，后台每 8 秒刷一次 = 每 8 秒卡一下，
滚动位置还会跳。现在先比结构签名（设备 + 变量名 + 控件形态），一致就只改数值、单位、上报时间、
状态胶囊这几格；用户正在某一格输入时不覆盖。

**五、变量名不再被截断。**
可写行右侧的「值 + 单位 + 写入 + 刷新」占掉约 132px，名字只剩 84px，「压缩机1运行状态」被截成
「压缩机…」。行高改为内容撑开、名字放不下就折第二行（`text-wrap:balance` 让两行字数接近），
变量名列下界 96px。

**六、变量置顶修「同类交错」。**
关键词「出水温度」也会命中「风机化霜出水温度1」。两段混在同一个名次里时，稳定排序只能按平台
返回顺序摆，置顶的四条被同类变量隔开。现在**完全等于**关键词的排第一段、只是**包含**的排第二段
（`varsort.py` 与界面 `vsRank` 同口径），四个温度先一个不留排完。

**七、顺手两处。**
右栏拖宽后卡片不再靠左留白（`.pvb` / `.pvpane` 缺 `box-sizing:border-box`，content-box 下宽度
比父容器多 32px，一直被裁）；日志框只留最近 400 行，不再开一整天堆上万行 DOM。
日志时间改用本机时间，原来是 `toISOString()` 的 UTC，排查时会差 8 小时。

### v1.4.2 新增

**一、左栏账号上的台数按当前站点筛选算。**
原来那个数取的是「上次巡站报告的总台数」，所以改完站点过滤不会有变化 ——
得再跑一次巡站才对，看着就像「加了 15 个站，还是 72 台」。
现在用已缓存的设备列表 + 最新的 `accounts.csv` 在本地数一遍，筛选一改立刻就对，不额外打平台接口。
和上次巡站的数不一致时，副标题会写成「78 台 · 上次巡站 在线 70 / 离线 8」，
徽标悬停能看到两个数各自的口径。监控引擎还没取到设备列表时，退回巡站统计。

**二、改了 `accounts.csv` 不用重启。**
账号表是纯文本，可以直接用系统编辑器改（也可以在另一个窗口改）。
界面每 30 秒对一次它的「修改时间 + 大小」指纹，变了就重画账号列表、并把设备列表的
60 秒缓存作废重拉。以前只有在本页点保存才认，直接改文件要等缓存过期或切页才看得到。

**三、实时卡每行多一列「最后上报时间」。**
以前每行写死「刚刚」，既对不齐也看不出真实时刻。现在显示这一路实际的上报时间：
当天 `15:42`、跨天 `10-19`，鼠标悬停看完整时间（到秒）。固定宽度右对齐成一列，
哪一路没在更新，扫一眼就知道。点某一行的单独刷新，只更新这一格，不整块重画。

### v1.4.1 新增

**一、变量可以置顶了。**

名字里带「修正 / 设定 / 原值 / 系数 / 补偿 / 偏置」的不参与排前

**三、修了一个显示问题。**
「设置 → 关闭按钮」以前看不到当前选的是哪一项，现在打开就显示真实值。

### v1.3.0 新增

**历史折线图重做。** 原来的图有三个说不通的地方，毛病是同一个——把「有数据的范围」当成了「用户选的范围」：

- **横轴只框住有数据的那一小段**。选「近 7 天」而本地记录只攒了 22 小时，横轴就缩成小时尺度，
  几天的空白被压成几小时，稀疏点之间再拉直线，看着像连续数据。现在横轴一律按「现在 − 所选范围 ~ 现在」
  铺满，没数据的区域就空着——空白本身也是信息（那段时间没有上报）。
- **跨天不按日期标刻度**。旧逻辑是跨度超过 3 天才标日期，于是选「近 3 天」时横轴还是小时刻度，
  一天里的哪个时刻根本对不上。现在跨度 ≥ 2 天就按**本地零点对齐**标 `MM-DD`，天数多自动隔几天取一格
  （最多 9 个）；一天以内按 `HH:MM` 均分。
- **断线判据是拍的间隔阈值**。本地落盘和云端平台都按「值没变就不记」瘦身，单看一个变量的缺口
  根本分不清「值没变」和「设备离线」；旧写法按间隔硬断，把一台 24 小时被采 307 次的设备的出水温度
  撕成了 4 截。现在后端额外下发**设备活动区间** `alive`（这台设备任何变量的记录时刻合并）和
  **程序活动区间** `run`（全部账号全部设备的记录时刻合并），前端按证据判：

  1. 缺口不超过心跳窗口 `hb`（本地 = 巡检周期 + 60 分钟）→ 正常节奏，连；
  2. 去掉两端 10 分钟（同一轮巡检各变量的平台时刻差几分钟，不能拿它当证据）后设备还有记录 → 值没变，连；
  3. 程序当时在跑、这台设备没声 → 真离线，断；
  4. 程序当时也没跑 → 没证据：缺口不超过一天猜它连着（机器是 24 小时开的），超过一天不猜，断。

  云端平台不补心跳，`hb = 0`、不给 `run`：并集静默就按「机器没开」处理。

配套两处小东西：**鼠标悬浮可看每个点**（多天尺度上稀疏点对不上刻度，得能逐个问出确切时间与数值）；
标题栏在记录还没攒够所选范围时标一句「数据自 MM-DD HH:MM」，否则用户会以为图画错了。
「无数据」只标在没有线的地方——设备活着、只是值没变被瘦身的空缺不标，那儿有线，标了自相矛盾。

**「并发线程」一处设置管两处。** 设置页这个数以前只管巡站截图，后台监控巡检在 `watch_engine.py` 里
写死 3：把设置调到 6 或 8，后台还是老速度，看着就是「设置没生效」。现在改完立即同步给巡检引擎；
跑截图时状态栏显示「截图中 3/46 · 6 线程」，启动日志里也打印一行「并发线程: 6 台同时处理」，
实际生效值看得见。

顺带修掉一个会把设置改回默认的 bug：截图请求没带 `workers`（或带 0）时，旧写法
`int(body.get('workers') or 4)` 会把用户存好的 6 悄悄改回 4。

### v1.3.0 修订（版本号不变）

**截图卡片把水温变量排到最前。** 每台设备只画前 `MAX_CARDS`（10）个变量，顺序是平台返回的
原始顺序 —— 平台那边是「谁先建的变量谁在前」。一台 17 个变量的机组，前十个位置常被
`水流量`、`定时运行使能`、`启动信号`、`T1修正` 占满，**供水 / 回水温度落在第 13、14 位，
直接被截断，截图里干脆没有温度**。

现在渲染前先按「水温优先」重排再截断，分三档（同档内用稳定排序，保持平台原顺序）：

| 档 | 判据 | 例子 |
| --- | --- | --- |
| 0 · 水温 | 名字里既有「水」又有温度字样 | 供水温度T1、回水温度T2、水温、水箱温度、循环水温度 |
| 1 · 其它温度 | 名字里有「温度」或以「温」结尾 | 室内温度T3、室外温度T4 |
| 2 · 其余 | 以上都不是 | 水流量、循环泵出口压力、定时运行使能、启动信号 |

三个细节：

- **先排序再截断**。搞反了等于没改 —— 水温变量早在第 11 位就被扔掉，图里照样没有温度。
- **只看变量名，不看单位**。单位要解析第 5 列的字符串，空值、异常格式都得兜；
  名字是用户自己起的，而且这个问题本来就出在名字上。
- **设定值和工程参数不算水温**。`水温设定`（设定值）、`制冷停止温度`（阈值）、`T1修正`（修正量）
  都留在原位置；`水流量`、`水压` 只有水没有温，也不进第 0 档。

浏览器渲染和 Pillow 本地渲染两条路径都改了（`render_mobile_cards` / `render_mobile_cards_pil`），
有浏览器和无浏览器环境看到的是同一个顺序。

### v1.2.0 新增

**「数据时间」改成按当前时钟实时走动。** 以前后端给的 `age_min` 是**巡检那一刻**算出来的
静态快照：10:30 巡检算出「1 分钟前」，到 11:00 界面上还写着「1 分钟前」。巡检 30 分钟一轮、
间隔又是 30 分钟，于是设备明明半小时没更新，看上去永远新鲜。

现在后端把**绝对数据时间** `newest`（平台记录的设备上报时刻）一起下发，前端每秒按本地时钟现算，
列表和实时卡片每 15 秒走一格，计数器会真的往上爬。

配套两处：
- **状态同步复判**：`status` 同样是巡检那一刻的判定。现在按当前时钟再判一次，
  越过 `stale_minutes` 就从「在线」改写为「数据陈旧」——不会再出现「在线 11 小时前」这种自相矛盾。
  阈值现读监控规则，改完保存立刻生效（不缓存）。
- **刷新成功即刷新时间**：单个变量刷新读到值的瞬间，把该设备的 `newest` / `age_min` 一起同步成「现在」，
  否则刚刷到的新数据还挂着上一轮的旧时间。

排序也改用复判后的状态与实时时间，避免「显示数据陈旧、却按在线排在最前」。
另外统一了「刚刚」的口径：不足 1 分钟都算刚刚（后端 `fmt_age` 原来写的是 `< 0`，跟前端对不上）。

### v1.2.0 修订（版本号不变）

**「设置 → 关于」加了仓库入口**：点「GitHub 主页 ›」用系统浏览器打开本仓库。

没有用网页内直接跳转。Electron 里 `<a href>` 会把主窗口本身导航走——没有地址栏、
退不回上一页，用户只能关掉重开。现在壳里用 `setWindowOpenHandler`（拦 `target="_blank"` /

`javascript:` / `file:` 这类 scheme 交给系统等于把命令执行权交出去。

## 二、从源码运行

需要 **Python 3.11+** 和 **Node.js**（仅用于装 Electron）。

```bash
# 1) Python 依赖
pip install pillow requests paho-mqtt

# 2) Electron（国内建议走镜像）
set ELECTRON_MIRROR=https://registry.npmmirror.com/-/binary/electron/   # Windows
export ELECTRON_MIRROR=https://registry.npmmirror.com/-/binary/electron/  # macOS / Linux
npm install

# 3) 启动
npm start
```

启动后先在「账号」页添加账号：名称 / 账号（手机号）/ 密码 / 平台 ID（默认 `W3rfV`）/ 站点过滤（留空＝该账号全部设备）。

## 三、使用免安装包（推荐）

Release 里给的是**免安装版**，解压即用，不需要装 Node.js 和 Python：

| 文件 | 平台 | 怎么用 |
| --- | --- | --- |
| `usrcloud-patrol-client-Windows-x64.zip` | Windows 10/11 x64 | 解压后双击 `有人云巡站客户端.exe` |
| `usrcloud-patrol-client-macOS-arm64.zip` | Apple Silicon Mac | 解压后把 `.app` 拖进「应用程序」，首次打开**必须右键**（见下一节） |

只有找不到内置解释器时才回落到系统 `python3`。

### macOS 未签名，首次打开怎么过门禁

本项目的 Mac 包**没有苹果开发者签名**（没有交 99 美元/年的开发者账号费用），
所以 macOS 的 Gatekeeper 会拦截，表现是双击后弹：

> 「有人云巡站客户端」已损坏，无法打开。您应该将它移到废纸篓。

**这不是文件损坏，也不是病毒**，只是系统不认识开发者。三种办法任选：

**办法一（推荐，最省事）**
1. 在访达里找到 `有人云巡站客户端.app`
2. **右键**（或按住 Control 点）→ 选「打开」
3. 弹窗里点「打开」

只需要做这一次，之后双击就能直接启动。

**办法二（用包内脚本）**
双击 zip 解压出来的 `解除门禁.command`，它会自动对 app 做一次去隔离属性处理。

**办法三（命令行）**
```bash
xattr -dr com.apple.quarantine "/Applications/有人云巡站客户端.app"
```

如果还想手动确认，可以看下签名状态：
```bash
spctl -a -vv "/Applications/有人云巡站客户端.app"
# 输出 "rejected" 是正常的，说明只是没签名，不是被判定为恶意软件
```

> 说明：只有从网上下载的 app 会被打上隔离属性（quarantine）。
> 自己编译的、或用 U 盘拷的，通常不会触发这个提示。

## 五、自行打包

1. 下载对应平台的 Electron 运行时（`electron-v44.5.1-win32-x64.zip`、`electron-v44.5.1-darwin-arm64.zip`）
